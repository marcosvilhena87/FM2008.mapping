## Avaliação e limites

**Há suporte dinâmico, em duas partidas, para o layout mínimo de identificação:**
```text
header = moduleBase + 0x0171ED4C
table = U32(header + 0)
count = I32(header + 4)
player = U32(table + 4 * index)
id = I32(player + 256)
firstName = legacyName(player + 280)
lastName = legacyName(player + 284)
commonName = legacyName(player + 288)

legacyName(slot):
  obj = U32(slot)
  if obj == 0: absent
  nested = U32(obj + 36)
  if nested == 0: absent
  utf16ptr = U32(nested + 8)
  if utf16ptr == 0: absent
  return UTF16LE_NUL_TERMINATED(utf16ptr, max 96 code units)
```

**Não foi demonstrado:** correspondência independente dos IDs com dados do jogo, validade de todas as entradas, estabilidade em outras builds, layout além dos campos de identificação, nem comportamento com relocação.

**Decisão de segurança:** manter `operational: false` no catálogo de pesquisa e `NoApprovedPlayerMaps` no editor principal. Uma eventual aprovação deve ser **restrita aos campos ID e nome**, após revisão da evidência e dos controles do leitor; não promove automaticamente os 229 offsets.

## Próximo passo técnico

Adicionar validação cruzada de alguns IDs diretamente no jogo, revisão dos invariantes e testes de erros com memória simulada. Só então propor um manifesto mínimo versionado e auditável, de leitura apenas.
